Archie Simulation Engine

How the architecture simulation works — what's real calculation, what's a placeholder, and what each component actually does in the equation.

1. The Simulation Loop

Every simulation runs 50 ticks over the challenge's duration (default 90s). At each tick:

For each tick t:
1. Interpolate target RPS from the traffic curve at time t
2. Inject traffic into entry nodes (nodes with no incoming edges)
3. Process nodes in topological order (DAG via Kahn's algorithm)
4. At each node: compare incoming traffic vs capacity → serve or shed
5. Forward served traffic to downstream nodes (even split at fan-out)
6. Record per-node telemetry (served, failed, latency, utilization) 
┌─────────────┐    inject RPS     ┌──────────────┐   forward    ┌──────────────┐
│Traffic Curve │───────────────────▶│  Entry Node  │─────────────▶│ Downstream   │
│ [t,rps]      │   (split evenly   │  (compute)   │  served RPS  │  (database)  │
│  points      │    across entries) │              │  only        │              │
└─────────────┘                    │ serve/shed   │              │ serve/shed   │
                                   └──────────────┘              └──────────────┘
                                   incoming > capacity?          incoming > capacity?
                                     YES → shed excess             YES → shed excess
                                     NO  → serve all              NO  → serve all

2. Per-Node Capacity Model

Every node in the simulation has three core properties from its component variant:

PropertySourceEffect
effectiveMaxRpsvariant.maxRPS × replicaCountThroughput cap — incoming above this is shed (dropped)
baseLatencyMsvariant.baseLatencyMsBaseline response time, grows under load
monthlyCostvariant.monthlyCost × replicaCountBudget scoring (not simulation mechanics)

Overload Behavior

If node is ONLINE and capacity > 0:
  served = min(incoming, capacity)
  failed = max(0, incoming - capacity)
  load = incoming / capacity
  latency = baseLatency × (1 + max(0, load - 1) × 2)

If node is OFFLINE (scheduled failure):
  served = 0, failed = incoming (all traffic shed)

If capacity = 0 (uncapped / unknown):
  served = incoming, failed = 0, latency = baseLatency

Latency under load: At 100% capacity, latency = base. At 200% capacity, latency = base × 3. Linear growth with overload factor LATENCY_LOAD_K = 2.

3. What Each Component Category Actually Does

Real simulation participant
Participates with limitations
Decorative / no flow

Compute REAL

Node.js, Python, Go, etc. Core request handler.

  • Capacity: 1k–4k RPS per variant
  • Latency: 8–25ms base; grows linearly under load
  • Scaling: Full replicas (×N capacity)
  • Requires: Upstream load balancer if replicated
  • Overload: Sheds excess traffic; latency spikes

Load Balancer / CDN REAL

Nginx, AWS ALB, Cloudflare CDN. Traffic distribution layer.

  • Capacity: 30k–500k RPS (CDNs have massive capacity)
  • Latency: 1–20ms base
  • Scaling: Full replicas
  • Special: actsAsLoadBalancer = true — satisfies the "upstream LB" topology requirement
  • Overload: Sheds excess (rare due to high capacity)

Database (SQL/NoSQL) REAL

PostgreSQL, MongoDB, DynamoDB, etc.

  • Capacity: 5k–50k RPS depending on variant
  • Latency: 2–15ms base
  • Scaling: Read-only replicas — reads scale, writes bottleneck at the writer
  • Overload: Sheds excess traffic; common bottleneck point

Cache (Redis, Memcached) REAL

In-memory data store for hot-path reads.

  • Capacity: 50k–200k RPS (very high, in-memory)
  • Latency: 0.5ms base (sub-millisecond)
  • Scaling: Full replicas (cluster mode)
  • Effect: Absorbs read traffic before it hits the database → reduces DB load

Message Queue REAL

RabbitMQ, Kafka, SQS. Async traffic decoupling.

  • Capacity: 5k–30k RPS
  • Latency: 2–5ms base
  • Scaling: Full replicas (distributed queues)
  • Effect: Absorbs burst traffic; downstream workers drain at their own pace
  • Limitation: No actual queueing model (v1) — just capacity + latency

Search Engine REAL

Elasticsearch, Algolia, Weaviate.

  • Capacity: 5k–30k RPS
  • Latency: 5–15ms base
  • Scaling: Read-only replicas
  • Effect: Offloads full-text search from the primary DB

Auth / Rate Limiter REAL

Auth0, rate-limiter, WAF. Security gate.

  • Capacity: 35k–100k RPS (high-throughput by design)
  • Latency: 1–10ms base
  • Scaling: Full replicas; requires upstream LB
  • Effect: Sits in the request path; adds latency; sheds when overloaded

Realtime (WebSocket) REAL

WebSocket server, Ably, Pusher.

  • Capacity: 5k–30k RPS
  • Latency: 2–5ms base
  • Scaling: Full replicas; requires upstream LB
  • Effect: Fan-out endpoint; participates in flow

Observability / Monitoring DECORATIVE

Prometheus, Grafana, Datadog.

  • Capacity: Has maxRPS (10k) but not in the critical path
  • Scaling: replicaType: "none" — singleton, no scaling
  • Effect: Does NOT carry request traffic. Exists for topology scoring and metric purposes. Adds cost but no flow impact.

Traffic Source SOURCE ONLY

Web Users, API Client, IoT Sensors.

  • Role: Originates all traffic — the entry point of the DAG
  • RPS: Discrete scale (3k → 10M via stepper)
  • Latency: 0ms (it's not a processing node)
  • Cost: Free
  • Effect: Determines the total load injected into the architecture

4. Scheduled Failure Events (Chaos)

Challenges can inject failures mid-simulation:

Event TypeTargetEffectDuration
component_failureSpecific nodeNode goes offline — all traffic shed (0 served)Specified in seconds
az_outageCategory (e.g. "compute")All nodes of that category go offline simultaneouslySpecified in seconds
latency_spikeSpecific nodeLatency multiplied (default ×3, stacks: ×3 × ×2 = ×6)Specified in seconds

Failure windows are half-open [t, t + duration). Multiple events can stack on the same node.

5. How Scoring Works

Uptime % = (totalServedRps / (totalServed + totalFailed)) × 100

System Latency (per tick) = max(node.latencyMs) across all nodes
p99 Latency = 99th percentile of per-tick system latencies

Star Rubric:
  Base pass (1★): uptime ≥ target AND p99 ≤ target AND all required_types present
  +1★: total cost ≤ budget cap
  +1★: zero topology issues (orphans, unreachable nodes)

10. Key Takeaways for Challenge Design

What the simulation actually tests:

  • Throughput bottlenecks: If any node in the path can't handle the traffic, RPS is shed → uptime drops
  • Latency chain: System latency = slowest node per tick. Overloaded nodes spike latency.
  • Cost efficiency: Total monthly cost of all nodes × replicas vs the budget cap
  • Topology correctness: No orphan nodes, no unreachable subgraphs, replicated nodes have LBs
  • Required blocks: The required_types field ensures the player uses the blocks the challenge teaches

What the simulation does NOT test:

  • Cache hit/miss ratios — a cache is just another capacity node
  • Write vs read traffic separation — all traffic is uniform
  • Message queue backpressure / retry semantics — queues are just capacity nodes
  • Database transaction isolation or consistency guarantees
  • Network partition modeling (only AZ outage which takes nodes fully offline)
  • Auto-scaling / elastic behavior (replicas are static during a run)
