Simulation Enhancement Proposals

Making component types matter — classified by complexity, importance, and impact on challenges.

The Core Problem

Today, the simulation treats all components as generic pipes — a Redis cache and a PostgreSQL database with the same maxRPS and latency are functionally identical in the engine. The rich component schema (ports, connection properties, data fit profiles) exists but has zero simulation impact. This means challenges can't test whether a player understands why they chose a specific component — only that they placed one.

2. Enhancement Proposals — Ranked

Each proposal is rated on three axes:

  • Complexity — how much code to change (Easy / Medium / Hard)
  • Importance — how much it matters for realistic simulation
  • Challenge Impact — how many new challenge types it enables

Tier 1: High Impact, Low Complexity (ship first)

E1: Cache Hit Ratio CRITICAL EASY

Add cache_hit_ratio: 0.8 to cache variants. Split incoming traffic: hits served at cache latency (0.5ms), misses forwarded downstream at full DB latency.

hit_traffic = incoming × cache_hit_ratio → served at 0.5ms
miss_traffic = incoming × (1 - ratio) → forwarded to downstream DB
Result: DB receives only 20% of traffic instead of 100%

Challenge enables: "Add a cache to reduce DB load" — player must tune the cache, not just place it. Without this, cache and DB are interchangeable pipes.

Components affected: Redis, Memcached (cache typeId)

Effort: ~50 lines in simulationEngine.ts + 2 YAML fields per cache variant

E2: Write vs Read Path Split CRITICAL EASY

Add write_ratio: 0.3 to data-storage variants. Split traffic into reads (scale with replicas) and writes (bottleneck at primary).

write_rps = incoming × write_ratio → capped at primary maxRPS (no replica help)
read_rps = incoming × (1 - write_ratio) → capped at maxRPS × replicaCount
Result: SQL single-primary bottlenecks on writes at scale

Challenge enables: "Why sharding matters" — player sees write bottleneck on SQL, learns when NoSQL sharding helps.

SQL vs NoSQL differentiation:

  • SQL (PostgreSQL): write_ratio: 0.3, writes go to primary only
  • NoSQL (MongoDB sharded): write_ratio: 0.3, writes distributed across shards (writes also scale)

Effort: ~40 lines in simulationEngine.ts + 1 YAML field per DB variant + 1 scaling rule flag

E3: CDN Edge Cache Bifurcation HIGH EASY

Add cache_hit_ratio: 0.85 + miss_latency_penalty_ms: 80 to CDN variants. Hits served from edge (10ms), misses add 80ms origin round-trip.

hit_traffic = incoming × 0.85 → latency = 10ms (edge)
miss_traffic = incoming × 0.15 → latency = 10ms + 80ms (origin fetch)
Result: CDN absorbs most static traffic but misses are expensive

Challenge enables: "Static vs dynamic content" — player learns CDN is great for static but misses hurt.

Effort: ~30 lines (reuse cache hit ratio logic) + 2 YAML fields per CDN variant

E4: Serverless Cold Start HIGH EASY

Add cold_start_latency_ms: 200 + cold_start_ratio: 0.1 to Lambda on-demand variants. 10% of requests pay cold start penalty.

effective_latency = baseLatency + cold_start_latency × cold_start_ratio
On-demand: 15ms + 200ms × 0.1 = 35ms average
Provisioned: 15ms + 0 = 15ms (no cold starts)

Challenge enables: "Provisioned vs on-demand" — player sees p99 spike from cold starts under burst traffic.

Effort: ~15 lines in simulationEngine.ts + 2 YAML fields

Tier 2: Medium Impact, Medium Complexity

E5: Queue Depth / Backpressure HIGH MEDIUM

Message queues absorb burst traffic into a buffer instead of shedding. Queue fills when consumers lag → latency increases with depth → eventually overflows and sheds.

queue_depth += (incoming - consumer_drain_rate) per tick
queue_latency = base + queue_depth × per_message_overhead
If queue_depth > max_queue_size: shed overflow
Result: Queues decouple producers from slow consumers (the actual point of a queue)

Differentiates: Kafka (durable, ordered, high buffer) vs RabbitMQ (fast drain, smaller buffer) vs SQS (auto-scaling buffer)

Challenge enables: "Decouple with a queue" — player sees why queues matter under burst (queue absorbs spike, workers drain steadily)

Effort: ~100 lines, new SimNode field queueModel, tick state tracks queue depth

E6: Interaction Rules Affect Capacity HIGH MEDIUM

Currently, category-pair rules (caching→data-storage) only adjust metric scores. Extend to adjust effective capacity too.

Current: cache→db only changes "read-latency" metric score by -2
Proposed: cache→db also reduces DB incoming traffic by cache_hit_ratio
AND: monitoring→compute adds 10% failure recovery bonus

Challenge enables: Every challenge where component placement affects downstream performance, not just topology presence.

Effort: ~80 lines, extend recalculator to feed back into SimNode properties

E7: Port Protocol Overhead MEDIUM MEDIUM

Different connection protocols add different latency overhead. HTTP adds serialization cost vs raw TCP.

Protocol overhead multipliers:
HTTP: 1.2× latency (JSON/REST serialization)
gRPC: 1.05× (binary, efficient)
TCP: 1.0× (baseline)
Memcached protocol: 0.9× (minimal framing)
Result: Choosing Redis (TCP) vs HTTP cache adds measurable latency difference

Challenge enables: "Protocol-aware architecture" — player learns that HTTP everywhere adds overhead.

Effort: ~60 lines, read connection_properties.protocol from each edge's nodes

E8: Monitoring Feedback Loop MEDIUM MEDIUM

If monitoring is connected to a node AND that node fails (scheduled failure), recovery is faster. Without monitoring, failures last longer.

With monitoring: failure duration = scheduled_duration
Without monitoring: failure duration = scheduled_duration × 1.5
Result: Monitoring isn't decorative — it actually reduces downtime

Challenge enables: "Observe Baseline" becomes meaningful — player sees that monitoring reduces the blast radius of failures.

Effort: ~40 lines in simulationEngine.ts failure handling

Tier 3: High Impact, High Complexity (future)

E9: Replication Lag Model MEDIUM HARD

Read replicas serve stale data during write bursts. Track replication lag; reads from replicas may return inconsistent results.

Differentiates: Strong consistency (SQL primary) vs eventual consistency (NoSQL replicas)

Effort: Major — needs consistency model in SimNode, per-replica state tracking

E10: Geographic Routing MEDIUM HARD

CDN and multi-region compute serve from the nearest PoP. Traffic source location affects latency to each node.

Differentiates: Global CDN (10ms everywhere) vs single-region compute (10ms local, 150ms cross-region)

Effort: Major — needs location model on nodes and traffic sources

E11: Auto-Scaling Elastic Behavior LOW HARD

Replicas scale up/down during simulation based on load. Scale-up has a ramp delay (30s to provision).

Differentiates: Pre-provisioned (instant) vs auto-scaling (delayed) vs serverless (per-request)

Effort: Major — per-tick replica count changes, ramp curves, cost tracking over time

5. The "Why It Matters for Challenges" Argument

Today's limitation

A challenge that says "Add a cache to improve performance" can only check that a cache exists on the canvas (via required_types). It cannot verify that the cache actually reduces database load because the simulation treats cache and DB as independent pipes. The player learns "put a cache here" but not why it helps.

With E1 + E2 + E6 implemented

A "Cache the Hot Path" challenge would actually show: database RPS drops from 3000 to 600 when a cache is placed upstream (80% hit ratio). A "Write Storm" challenge would show SQL bottlenecking on writes while MongoDB sharded handles the same load. The player learns the mechanism, not just the topology.
