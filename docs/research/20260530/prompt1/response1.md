## 3. Component-taxonomy deep-dive (focus area)

**Validation of your hypothesis: confirmed.** Archie's `component_id`s *are* providers and `config_variant_id`s are deployment topologies of that single provider — e.g. `cloudflare-cdn → {static-caching, full-site}`, `postgresql → {single-node, primary-replica, citus-distributed}`, `nginx → {reverse-proxy, load-balancer}`. There is no layer to swap Cloudflare for Fastly. The Reference app already implements the target model: a **CDN** type whose node dropdown lists providers, each with its own `$ · RPS · ms` profile (DNS dropdown showed Route 53 $5·80k·1ms, Cloudflare $0·40k·1ms, Cloud DNS $3·60k·2ms, Azure $8·150k·1ms; SQL showed Postgres/MySQL/Aurora/Cloud SQL with distinct throughput/latency).

**Recommended fundamental-type list (covers Archie's 10 categories):**
Compute/Service, Serverless Function, Load Balancer, API Gateway, CDN, DNS, Relational Database, NoSQL Database, Cache, Object Storage, Search, Vector Store, Message Queue, Stream/Event Bus, Real-Time/WebSocket, Observability/Monitoring, Auth & Security (WAF/SIEM), Payments, ETL/Data Pipeline, LLM Gateway.

**Type → Provider → Tier model:**
- *Type* = the concept the user reasons about (e.g., Cache).
- *Provider* = the implementation, each carrying its own price + capability profile (Redis / Memcached / DynamoDB DAX).
- *Tier* = the deployment topology/size within a provider (Redis: standalone / sentinel / cluster) — this is exactly what Archie's existing "config variants" become.

Pattern: pick a **type** from the toolbox (concept-first, with search across type + synonyms/tags), drop a generic node, then choose **provider** and **tier** in the inspector — reusing Archie's existing variant dropdown and its nice delta indicators (+25 / +400000 / −10ms I saw on the CDN).

**Migration notes (your ~18 components / 10 categories):**
- *Maps cleanly:* `postgresql` → Relational DB / Postgres; `cloudflare-cdn` → CDN / Cloudflare; `nginx` → split its two variants — `reverse-proxy` stays Compute-adjacent (API Gateway/Service), `load-balancer` becomes the **Load Balancer** type; `kafka` → Stream/Event Bus / Kafka; `rabbitmq` → Message Queue / RabbitMQ; `prometheus` → Observability / Prometheus; `websocket-server` → Real-Time. Existing variant IDs become **tiers** verbatim.
- *Needs re-grouping:* `redis` + `redis-cache` collapse into one **Cache** type (Redis provider; modes become tiers) — removes the duplicate. `node-express` becomes Compute/Service with Node.js as the provider and `single-process/cluster-mode` as tiers.
- *Breaks / needs new homes:* `payment-gateway`, `llm-gateway`, `etl-pipeline`, `siem`, `data-lake`, `vector-database` are currently single-provider stand-ins. Promote each to a **type** (Payments, LLM Gateway, ETL, Security/SIEM, Object Storage/Data Lake, Vector Store) and seed 1–3 providers under each so the model is consistent even where Archie ships one option today.
- *Schema impact:* keep `component_id` + `config_variant_id`, add a `provider_id` between them (`type_id / provider_id / variant_id`). Old YAML can be migrated with a static map (`cloudflare-cdn` → `cdn/cloudflare`, etc.), so the AI-Prompt and Import paths stay lossless.
