I rebuilt in Coding Ducks from a clean slate (reset the canvas, then added DNS, wired it to Users, swapped its provider, added and removed a Cache) so I could test the editing model directly rather than just reading the finished challenge. Here's the deeper analysis, organized around the two things you flagged — information density and the abstraction layer — plus the editing affordances that fall out of them.

## Why the left side reads as denser and clearer in Coding Ducks

The difference isn't that Coding Ducks shows *less* information — it shows roughly the same facts but spends far less vertical space and cognitive load per item. Each palette entry is a compact two-per-row tile: icon, a **concept name** (DNS, CDN, Load Balancer, Cache, Search Engine), and a **price range** ($0–$8, $20–$55) — about three text lines tall. Seventeen block types across five categories (Networking, Compute, Storage, Messaging, Security) fit in roughly one screen, and each category header is **collapsible** (I collapsed Compute and the rest reflowed immediately), so the user controls density. The full menu of "what can I add" is legible at a glance.

Archie's palette does the opposite: every component is a tall card carrying a description plus IS / GAIN / COST bullet lists, tag chips, and a price — easily 15–20 lines each. You can only see two or three components without scrolling, and the bullets are *reference material*, not selection cues. The information is valuable, but it's the wrong information for the moment of "pick something to place." Coding Ducks defers that depth: the tile gives you name + price to choose, and the rich tradeoff data appears only when you need it (in the node's provider dropdown). That deferral is the whole density trick.

The same pattern repeats on the canvas. A Coding Ducks node is essentially one compact card — type, provider, $/mo, a provider dropdown, and a replica stepper. An Archie node, once selected, drives a right-hand Inspector with four tabs and ~8 stacked sections including a full YAML/wrangler.toml block that dominates the panel. Everything is expanded at once with no hierarchy, which is the "quickly becoming very confusing" you described.

## Why the abstraction layer is genuinely better, demonstrated from scratch

When I dropped a fresh **DNS** block, it placed as a generic *type* defaulted to Route 53, and its provider dropdown listed Route 53 ($5 · 80k RPS), Cloudflare DNS ($0 · 40k), Cloud DNS ($3 · 60k), Azure DNS ($8 · 150k) — each implementation with its own price·throughput·latency profile, selectable in place. So the model is exactly type → provider → (tier/replicas), and the user reasons in concepts first ("I need a DNS") and only then weighs implementations, with the tradeoffs surfaced at the decision point. Archie inverts this: the thing you place *is* the provider (Cloudflare CDN, Nginx, PostgreSQL, Redis), and its dropdown only switches that one provider's deployment mode (Static-Caching ↔ Full-Site). You can't express "a CDN, undecided," and you can't compare Cloudflare vs. Fastly without knowing brands up front. That's why the abstraction feels heavier even though Archie arguably has *more* data — it's asking the user to start at the most specific layer.

There's a second payoff I saw live: because types are first-class, Coding Ducks can run **real-time topology validation against them**. Adding an unconnected Cache immediately produced "⚠ Cache is placed but not connected to traffic," and the right-side **Required checklist** (Dns, Cdn, Firewall, Rate Limiter, Api Gateway, App Server, Sql Db) flipped "Dns" to a green ✓ the instant I wired DNS to Users. A bottom step tracker ("① Add blocks → ② Connect & place required") advanced as I went. Archie's guidance is static hint bullets; it can't give live "you're missing a type / this isn't on the traffic path" feedback as cleanly because its graph is keyed on providers, not roles.

## The editing affordances — confirmed, and they follow from the same philosophy

Selecting any node in Coding Ducks pops a small floating toolbar **directly above the node** with labeled **Duplicate** and **Remove** buttons. I clicked Remove on the orphan Cache and it deleted instantly, the budget recalculated $568→$533, and the topology warning cleared. Actions live on the object, where the cursor already is. Archie has no such control: I scrolled the entire component Inspector and the entire connection Inspector to the bottom and there is no Remove button on either; deletion only works via the Delete key (it did remove both a node and an edge in my tests), which is undiscoverable — and for connectors there is no on-screen path at all. So this isn't only a polish gap; removing a wrong connection in Archie is currently a hidden keyboard-only action.

Wiring difficulty traces to the same place. In Coding Ducks my very first port drag (Users → DNS) connected cleanly; in Archie my drags repeatedly grabbed the node body instead of the port handle. Bigger, clearer port targets plus on-object controls are why their canvas feels lighter to operate.

## Concrete, prioritized revisions for Archie

1. **Demote palette cards to compact rows.** Make each component a two-per-row tile of icon + name + price range, with categories collapsible. Move the IS/GAIN/COST detail to hover or to the Inspector. This alone roughly triples how many components are visible and stops the toolbox from competing with the canvas. (Evidence: Coding Ducks palette vs. Archie's tall cards.)

2. **Add on-object node and edge toolbars with Duplicate + Remove.** Show them on selection, floating at the node/edge, mirroring Coding Ducks. This fixes the single functional gap — connectors that can't be deleted from the UI — and makes node deletion discoverable. Keep the Delete-key shortcut as the accelerator. (Evidence: Coding Ducks Duplicate/Remove toolbar; Archie inspectors with no delete.)

3. **Collapse the Inspector by default into a hierarchy.** Top: name, provider/variant, the $ · throughput · latency line, and the Remove button. Below: collapsed disclosures for YAML, Gains/Costs, Recommendations, and Metrics. The raw config should never be the first thing a user sees. (Evidence: Archie's 4-tab, ~8-section, YAML-dominated panel.)

4. **Introduce the type → provider → tier model and a live Required/topology check.** Place generic types; choose provider+tier in the node dropdown with price·throughput·latency shown inline; then drive a live "missing type / not connected to traffic" checklist like theirs. This is the larger bet but it's what makes the lighter UI *and* the better guidance possible. (Evidence: fresh DNS provider dropdown; Cache topology warning; Required checklist ticking live.)

5. **Make wiring forgiving.** Enlarge port hit-areas, highlight ports on node hover, and offer a click-source-then-click-target fallback. (Evidence: first-try connect in Coding Ducks vs. repeated mis-grabs in Archie.)
